Toward Deployable Hardware Roots of Trust for Edge AI: Software PUFs and Their Trade-offs

Yilin Li and Farhad Merchant, University of Groningen.

Abstract · PDF

Plain English

The paper surveys 37 software PUF methods. Each one derives a unique, repeatable device fingerprint from chips that are already there: memory start-up values, DRAM timing and decay, flash, processor timing, or motion sensors. It uses only software, so a secret key never has to be stored on the device. The survey compares how unique and reliable each method is, how fast it answers (microseconds to minutes), and whether it works while the device is running. Four problems stay open. Low-level hardware access is often locked by firmware. Enough randomness has to remain after error correction. Some methods are too slow to use while a program is running. The attacker model is not always clear: someone who controls the operating system could replay or tamper with the answer.

Why it matters for lgme.app

lgme already binds trust to the device: passkey and fingerprint unlock are planned, the tape stays on the device, and Sources can use on-device AI. A fingerprint like this could later strengthen a “one device, one member” check and protect on-device keys and models without new hardware. It needs kernel or firmware access that a web app does not have. For now, WebAuthn passkeys, which use the phone’s secure chip, remain the practical path. Software PUFs are a watch item, not a build item.

Open questions

  • Could a phone vendor or a wallet expose a PUF-backed key through WebAuthn?
  • Can it help stop duplicate accounts in the campus pilot without collecting personal data?
